By the end of this page, you'll have a project set up, a branch open in a workspace of its own, its dev server running and your machine clean again. It takes about ten minutes, and it's the loop you'll use for every pull request you review.

## Before you start

You'll need two things:

- Testlane, [installed](/docs/getting-started/installation) so that `testlane version` runs.
- A git repository you can clone, with a branch to try. We'll call the project `my-project` and the branch `feat/login`.

## Set up your first workspace

::steps{level="3"}

### Set up the project

`testlane setup` creates the config directory, `~/.testlane` by default, sets the base directory for clones and workspaces, and writes your first project file. In a terminal it asks for each value, and each one is also a flag, so the same command runs without a prompt:

:::code-group

```bash [interactive]
testlane setup
```

```bash [non-interactive]
testlane setup --name my-project --repo git@github.com:my-org/my-project.git --yes
```

:::

To see what it would write first, add `--dry-run`, which prints the plan and changes nothing:

```bash
testlane setup --name my-project --repo git@github.com:my-org/my-project.git --dry-run --yes
```

```
mkdir -p /home/you/.testlane
write /home/you/.testlane/defaults.toml
  root = "~/dev/testlane"
write /home/you/.testlane/my-project.toml
  repo = "git@github.com:my-org/my-project.git"
```

The plan shows the full paths, so you can see where each file goes.

### Teach it how to run

`setup` writes only the repository. Open the project file and add the two things Testlane needs to make a workspace runnable, how to install dependencies and what your commands are:

```bash
testlane config edit my-project
```

```toml [~/.testlane/my-project.toml]
repo = "git@github.com:my-org/my-project.git"
default_branch = "main"
editor = "code"

[setup]
run = "pnpm install --frozen-lockfile"
cache_key = ["pnpm-lock.yaml"]

[env]
PORT = "{port}"

[commands.dev]
run = "pnpm dev"
```

`{port}` is a [template variable](/docs/configuration/environment-and-templates) for the workspace's own port, so two dev servers never reach for the same one. `default_branch` is the branch `diff` compares a workspace against, so set it to yours. Note that the file leaves out `repo_path` and `worktrees_path`, since they default to `{root}/{project}/repo` and `{root}/{project}/trees`. [Configuration](/docs/configuration/overview) has every key.

### Check your setup

`doctor` checks your tools, your config directory and every project you've set up:

```bash
testlane doctor
```

```
OK   git version: git 2.50.1
OK   gh (github cli): authenticated
OK   config dir: /home/you/.testlane
OK   state dir: /home/you/.local/state/testlane
OK   project my-project: config: schema-valid
OK   project my-project: repo: not yet cloned; parent writable (/home/you/dev/testlane/my-project/repo)
OK   project my-project: editor: code (/usr/local/bin/code)
```

A `WARN` line, like the editor line when `code` isn't on your `PATH`, doesn't stop anything. A failed check makes `doctor` exit with `1`, so it works in CI too. To check only the project files, run `testlane config validate`.

### Open a branch

Now let's run the pipeline. Give it a ref, like a branch name, a PR number or a full commit SHA:

```bash
testlane my-project feat/login checkout
```

```
→ cloning git@github.com:my-org/my-project.git (bare, partial)
→ fetching origin/feat/login
→ worktree ready: /home/you/dev/testlane/my-project/trees/feat-login
/home/you/dev/testlane/my-project/trees/feat-login
```

The first ref clones the repository once, and every ref after it reuses that clone, so the next workspace only fetches. `checkout` prints the workspace's path on stdout and nothing else, so you can use it in a script:

```bash
cd "$(testlane my-project feat/login checkout)"
```

### Run something in it

`run` opens the same workspace, runs the `[setup]` install, then runs a command from your project file inside it:

```bash
testlane my-project feat/login run dev
```

```
→ worktree ready (reused)
→ running setup
…
listening on 4153
```

The next `run` skips the install while `pnpm-lock.yaml` stays the same. There are other ways to act on the same workspace:

```bash
testlane my-project feat/login code                         # open it in your editor
testlane my-project feat/login shell                        # a shell with the workspace's variables
testlane my-project feat/login exec -- git log --oneline -2 # any command, run without a shell
testlane my-project feat/login diff --stat                  # what the branch changes
```

### See what you have

```bash
testlane my-project list
```

```
SLUG        KIND    BRANCH      STATUS  PORT  AGE  LAST USED
feat-login  branch  feat/login  clean   4153  0m   0m
```

In a terminal, a bare `testlane my-project` turns that list into a picker and prints the path of the workspace you choose.

### Clean up

```bash
testlane my-project clean --all --yes
```

```
→ plan:
  feat-login (clean, 16 KB)
feat-login
→ freed 16 KB
```

`clean` prints its plan and asks before it removes anything, and `--yes` answers for you. Day to day, you'll want its filters instead, like `--merged`, `--closed` or `--older-than 7d`. [Clean up workspaces](/docs/guides/clean-up-workspaces) covers each one.
